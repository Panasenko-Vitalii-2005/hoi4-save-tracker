# Single-file analysis persistence

`POST /api/analyze` keeps its existing HTTP 201 and unchanged `AnalyzeResult` JSON when computation succeeds. Single-file responses additionally include:

- `X-Analysis-Persistence: saved`: the completed artifact (atomic write, file sync and rename, or validated identical artifact reuse), Recent metadata commit, and PostgreSQL ownership/history projection commit all succeeded. The artifact fingerprint and compact history projection must be valid before ownership is committed.
- `X-Analysis-Persistence: temporary`: computation succeeded, but that durable operation could not be confirmed. Quota exhaustion, artifact write/publication failure, metadata failure, unavailable final artifact, and ownership database failure all use this outcome. The full computed JSON remains available immediately.
- `X-Analysis-Hash` is emitted **only for saved outcomes**, with the unchanged SHA-256 save identity. Both headers are exposed by credentialed CORS; request/auth/CSRF rules are unchanged. Persistence metadata is not added to the parser result, RAM cache or persisted result envelope.

The UI keeps a temporary result viewable/exportable, with EN/RU recovery guidance and an explicit Retry saving action. It does not attach a saved-result identifier, so temporary opens/section views are not reported as owned saved analyses. Saved Compare, Trends, Intelligence, sharing and reopening continue to use ownership plus retained artifacts, never the currently displayed temporary result. Selecting another file or a failed retry does not erase the displayed result's notice. A successful reopen replaces it with the saved state. Responses from older servers with no outcome header are shown as unconfirmed, not assumed saved just because a hash exists.

Retrying explicitly resends the original save through the existing upload endpoint. It reuses the bounded RAM analysis cache when available, without rerunning the Worker. A valid artifact whose full result and comparison context exactly match is reused under the existing serialized write queue, including after service restart or a failed ownership commit. Different/corrupt artifacts retain the existing atomic replacement path. No new recovery endpoint, automatic retry, quota increase, cleanup policy, migration or persistence format is introduced. After cache eviction/server restart, an upload may need analysis again.

`?response=batch` retains its compact success payload and explicit HTTP 503 `PERSISTENCE_FAILED` path; ownership failures now also consistently use that persistence code rather than `ANALYZER_BUSY`. Sequential batching and preflight authorization are unchanged.

Filesystem and PostgreSQL commits are not a distributed transaction. A metadata/ownership failure can leave an unowned physical artifact; it is not thereby a private saved analysis. No rollback deletes an existing artifact, share or ownership. A database acknowledgement failure can be ambiguous after commit, so the API conservatively declines to confirm saving; a previously owned analysis may still exist independently. The response attests to successful persistence at operation completion, not indefinite retention or availability after concurrent explicit deletion, disk loss or later corruption. Existing backup/retention behavior remains unchanged. Analysis-completed telemetry still means computation completed, not durable persistence; saved-analysis client telemetry requires the explicit saved outcome.

Local acceptance: force a test-only storage cap or write/metadata/ownership failure; confirm HTTP 201, `temporary`, no hash, visible result and warning, no newly owned history/preflight/share access. Remove the injected failure and retry; confirm `saved`, hash, reopening/history access and unchanged result identity. Never perform failure injection against production data.
